# Media Control Bot 使用指南

## 1. 环境与配置

本程序面向 Linux VPS。安装 Rust/Cargo、FFmpeg 和 FFprobe，创建媒体目录并确认运行用户有读写权限；合并与转封装需要在媒体盘创建临时文件。复制 [`.env.example`](.env.example) 为 `.env`，至少填写：

```dotenv
BOT_TOKEN=你的_Telegram_Bot_Token
ADMIN_ID=你的_Telegram_数字_ID
BASE_DIR=/storage512/bilivego/download
STORAGE_MOUNT_POINT=/storage512
RTMP_URL=
```

`BOT_TOKEN` 和 `ADMIN_ID` 必填；`BASE_DIR` 是文件操作边界。`STORAGE_MOUNT_POINT` 默认 `/storage512`，程序会核验它是否为独立真实挂载。若使用别的媒体盘，同时调整这两个路径。`RTMP_URL` 可留空；未配置时无法推流。`.env` 中的相对状态文件路径以进程工作目录为准。

常用可选项见下表，完整列表及取值说明以 [`.env.example`](.env.example) 为准。

| 配置 | 默认值 | 用途 |
| --- | --- | --- |
| `ITEMS_PER_PAGE` | `8` | 文件列表分页。 |
| `FILE_STABLE_SECONDS` | `30` | 文件最近修改后的静置时间；`0` 关闭。 |
| `TRASH_RETENTION_DAYS` | `7` | 回收站保留天数。 |
| `DISK_CHECK_INTERVAL_SECS` | `300` | 后台磁盘巡检间隔。 |
| `DISK_ALERT_RESET_L1/L2/L3` | `85/90/95` | 三档报警的回落复位百分比。 |
| `YOUTUBE_MAX_CONCURRENT_UPLOADS` | `2` | 同时运行的上传数。 |
| `YOUTUBE_MAX_QUEUE_SIZE` | `10` | 额外排队任务数。 |
| `YOUTUBE_UPLOAD_CHUNK_MB` | `10` | 单次上传分块大小。 |
| `YOUTUBE_RECOVERY_MODE` | `none` | `none`、`requeue` 或 `resume`。 |
| `MERGE_ALLOW_AUTO_TRIM` | `false` | 是否允许合并时自动截除损坏片尾。 |

将 `.env`、YouTube `token.json` 以及上传/告警状态文件限制为部署用户可读，勿提交到仓库。

## 2. 构建与运行

```bash
cd vps-telegram-bot/media-control-bot
cargo build --release
./target/release/media-control-bot
```

确认 Telegram 中 `/start` 显示预期媒体根目录和挂载状态，再执行写入操作。只运行一个使用该 `BOT_TOKEN` 的实例，避免 Telegram 更新轮询冲突。

需要常驻运行时，可创建 `/etc/systemd/system/media-control-bot.service`，把路径和用户改成实际值：

```ini
[Unit]
Description=Media Control Bot
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=media
WorkingDirectory=/opt/media-control-bot
ExecStart=/opt/media-control-bot/target/release/media-control-bot
Environment=PATH=/usr/local/bin:/usr/bin:/bin
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now media-control-bot
sudo journalctl -u media-control-bot -f
```

## 3. 媒体操作

`/start` 打开菜单。浏览器只列出支持的媒体扩展名；可用 `/find 关键词` 和 `/clearfilter` 控制列表。菜单快照用于检测目录变化，旧按钮失效时重新打开当前目录。

合并按点击顺序处理文件。程序先检查流参数及可用空间，再尝试 concat 和 TS 中转等无损方案。结果通过探针与时长校验后发布，源文件保留。默认 `MERGE_ALLOW_AUTO_TRIM=false`：若只有截掉少量损坏片尾才能修复，程序提示候选方案，需由管理员决定是否开启自动截除。转封装也只复制音视频流，无法保证任意编码都适合 MP4。

推流需要有效的 `RTMP_URL`，采用流复制。FFmpeg 本地成功退出只代表源文件发送完毕，应到目标平台确认直播画面。删除先进入同盘回收站，`/trash` 可恢复或永久清空；清空后无法通过机器人恢复。

## 4. YouTube 上传

上传使用 OAuth2 `authorized_user` 凭据文件，所需 scope 为 `https://www.googleapis.com/auth/youtube.upload`。在 `.env` 中设置 `TOKEN_FILE` 的绝对路径。上传任务受并发和队列上限控制；`/uploads` 查看进度，`/stop` 取消。只有收到服务端完成响应和有效视频 ID 后才报告成功。

默认 `YOUTUBE_RECOVERY_MODE=none`，服务重启不会自动恢复上传。选择 `requeue` 或 `resume` 时，指定安全位置的 `YOUTUBE_UPLOAD_QUEUE_FILE`；`/pending` 可查看需要核实的会话。重启后先确认远端状态，避免重复上传。

## 5. 磁盘告警与排错

程序启动、返回主菜单及后台巡检时检查挂载和容量，超过 90%、95%、98% 分别触发不同级别通知，降到复位阈值后允许再次通知。若界面显示挂载不可用，先运行 `findmnt /storage512` 和 `df -h /storage512`，再检查 `STORAGE_MOUNT_POINT` 设置。

| 现象 | 检查方向 |
| --- | --- |
| `/start` 无响应 | 服务日志、Token、`ADMIN_ID`、是否有另一实例使用同一 Token。 |
| 合并或转封装失败 | FFmpeg/FFprobe 是否可用、源流兼容性、临时空间和媒体目录权限。 |
| 推流断开 | RTMP 地址、网络连接及目标平台对源音视频编码的支持。 |
| YouTube 上传失败 | `TOKEN_FILE` 权限、OAuth scope、授权是否有效及服务端返回信息。 |

程序监听 Ctrl+C 与 systemd 默认的 SIGTERM，停机时会取消任务并清理子进程；实际文件和远端上传状态仍应在重启后核对。
